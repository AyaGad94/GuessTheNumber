# Guess The Number

A full-stack interview assessment project built with **React**, **ASP.NET Core Web API**, and **PostgreSQL**.

The application allows users to register, log in, play a Guess the Number game, receive higher/lower hints, and keep their **best score** — the lowest number of guesses used to complete a game.

> **Interview brief:** Build a simple full-stack CRUD application using React and PostgreSQL within 2 days, store it on GitHub, and deploy it to AWS or another cloud platform.

# Main Features

## Authentication

Users can:

- Register with username, email, and password
- Log in with email and password
- Remain authenticated while the browser session is active
- Log out by clearing the client-side authentication token
- Return later and see their saved `BestScore`

The backend uses **JWT Bearer authentication**.

Protected endpoints require:

```http
Authorization: Bearer <JWT>
```

The JWT is generated by the backend after a successful login.

The frontend stores the token in `sessionStorage`.

---

## Registration

The frontend sends:

```http
POST /api/auth/register
```

Example request:

```json
{
  "username": "PlayerOne",
  "email": "player@example.com",
  "password": "ExamplePassword123"
}
```

The backend:

1. Validates the input
2. Normalizes the email
3. Checks that the email is unique
4. Hashes the password with ASP.NET Core `PasswordHasher<TUser>`
5. Stores the user in PostgreSQL
6. Returns only safe user information

Passwords are **never stored as plain text**.

---

## Login

The frontend sends:

```http
POST /api/auth/login
```

Example request:

```json
{
  "email": "player@example.com",
  "password": "ExamplePassword123"
}
```

A successful response contains:

```json
{
  "token": "<JWT>",
  "expiresAtUtc": "<UTC timestamp>",
  "user": {
    "id": 1,
    "username": "PlayerOne",
    "email": "player@example.com",
    "bestScore": null
  }
}
```

For security, an unknown email and an incorrect password both return the same generic message:

```text
Invalid email or password.
```

This avoids exposing whether an email is registered.

---

## Restore Authentication

When the frontend refreshes, it reads the JWT from `sessionStorage` and calls:

```http
GET /api/auth/me
```

The backend validates the JWT and returns the current user.

This lets the UI restore:

- Username
- Email
- Best score

---

## Logout

The application uses stateless JWT authentication.

Logout is handled by removing the JWT from the browser:

```javascript
sessionStorage.removeItem("authToken");
```

There is intentionally no fake backend logout endpoint.

The JWT technically remains valid until its expiry time, but the client no longer sends it after logout.

# Guess The Number Game

## Rules

- The server generates a random integer from **1 through 43**
- The target number is never sent to the frontend
- The authenticated user submits guesses
- If the guess is too low, the API responds with `Guess higher.`
- If the guess is too high, the API responds with `Guess lower.`
- Each submitted guess counts as one attempt
- A repeated guess also counts as another attempt
- When the user guesses correctly:
  - The game ends
  - The final attempt count is calculated
  - The user's `BestScore` is updated only if the new score is better

---

## Start Game

```http
POST /api/game/start
Authorization: Bearer <JWT>
```

The backend creates the target number using:

```csharp
RandomNumberGenerator.GetInt32(1, 44)
```

The upper limit is exclusive, so this produces values from `1` through `43`.

The target number remains server-side.

---

## Submit Guess

```http
POST /api/game/guess
Authorization: Bearer <JWT>
Content-Type: application/json
```

Request:

```json
{
  "guessedNumber": 20
}
```

Example incorrect response:

```json
{
  "message": "Guess higher.",
  "attemptCount": 1,
  "isCorrect": false,
  "bestScore": null,
  "isNewBestScore": false
}
```

Example winning response:

```json
{
  "message": "Correct!",
  "attemptCount": 4,
  "isCorrect": true,
  "bestScore": 4,
  "isNewBestScore": true
}
```

# Best Score Design

The interview brief asks to keep track of the lowest number of guesses in the database and to keep track of one field.

The application implements that requirement with:

```text
Users.BestScore
```

`BestScore` is nullable.

A new user begins with:

```text
BestScore = NULL
```

If a user completes a game in 7 guesses:

```text
BestScore = 7
```

If the next game takes 10 guesses:

```text
BestScore remains 7
```

If a later game takes 4 guesses:

```text
BestScore becomes 4
```

The backend is the only layer allowed to update `BestScore`.

The frontend cannot submit or directly control the stored score.

---

# Concurrency-Safe Best Score Update

The backend performs a conditional database update:

```text
Update BestScore only when:

BestScore IS NULL
OR
BestScore > new attempt count
```

This prevents a worse score from overwriting a better score if multiple requests race.

The game service uses EF Core's direct update support so a full tracked `User` entity does not need to be loaded just to update one field.

### Responsibilities

- Collects login credentials
- Calls `loginUser()`
- Passes the successful authentication response to `App.jsx`

- Starts games

`App.jsx`
- Owns authenticated-user state
- Owns JWT state
- Restores authentication
- Handles logout
- Displays the current best score
- Hosts the game component

# Game Session Design

Active games are currently stored in backend memory.

Each active game stores:

```text
User ID
Target number
Attempt count
```

The authenticated user ID is used as the key.

Important behavior:

- Starting a new game replaces any existing active game for that user
- Correctly guessing the number removes the active game
- BestScore is persistent because it is stored in PostgreSQL
- Active game state is not persistent across an API restart

For this assessment's single-instance deployment, this keeps the implementation simple and easy to explain.

For a larger distributed system, active game sessions could be moved to a shared store such as Redis.

# Security Decisions

The application includes the following security measures:

- Passwords are hashed using ASP.NET Core `PasswordHasher<User>`
- Plain-text passwords are never stored
- JWT signing key is not committed to Git
- Database password is not committed to Git
- Production configuration files containing secrets are ignored
- Game endpoints use `[Authorize]`
- User ID is taken from the authenticated JWT rather than from client input
- The random game target stays server-side
- The frontend cannot set `BestScore`
- Duplicate emails are protected by both application checks and a database unique constraint
- Login uses a generic invalid-credentials message
- CORS allows only configured frontend origins

# Local Development Setup

## Prerequisites

Install:

- Git
- .NET 9 SDK
- Node.js
- npm
- Docker Desktop
- pgAdmin 4 is optional but useful for viewing PostgreSQL data

## 1. Clone the Repository

```bash
git clone https://github.com/AyaGad94/GuessTheNumber.git
cd GuessTheNumber
```

## 2. Configure Local PostgreSQL

Create a local root `.env` file:

```env
POSTGRES_DB=guess_number_db
POSTGRES_USER=guessapp
POSTGRES_PASSWORD=your_local_password
```

Do not commit the real `.env` file.

Start PostgreSQL:

```bash
docker compose up -d
```

Check the container:

```bash
docker ps
```

## 3. Configure Backend Secrets

The backend requires:

```text
ConnectionStrings:DefaultConnection
Jwt:Key
```

Store them using .NET User Secrets:

```bash
cd backend/GuessTheNumber.Api

dotnet user-secrets set "ConnectionStrings:DefaultConnection" "<your-local-postgresql-connection-string>"
dotnet user-secrets set "Jwt:Key" "<your-base64-jwt-signing-key>"
```

## 4. Apply EF Core Migrations

```bash
dotnet ef database update
```

## 5. Run the Backend

```bash
dotnet run
```

Local API:

```text
http://localhost:5124
```

## 6. Configure the Frontend

Create:

```text
frontend/.env.local
```

with:

```env
VITE_API_BASE_URL=http://localhost:5124
```

Never place secrets in `VITE_*` variables because Vite exposes them to browser JavaScript.

## 7. Install Frontend Dependencies

```bash
cd frontend
npm install
```

## 8. Run the Frontend

```bash
npm run dev
```

Local frontend:

```text
http://localhost:5173
```

# Performance Considerations

The backend intentionally uses efficient database-access patterns:

- Async EF Core calls
- `CancellationToken` where appropriate
- `AsNoTracking()` for read-only queries
- Projection with `Select()` when full entities are unnecessary
- Minimal database round trips
- Direct conditional `ExecuteUpdateAsync()` for BestScore
- No database query for incorrect game guesses

Typical game behavior:

```text
Wrong guess:
0 database operations

Winning guess that is not a new best:
1 lightweight projected SELECT

Winning guess that may be a new best:
1 projected SELECT
1 conditional UPDATE

Rare concurrent score race:
1 additional SELECT to return the latest score
```

---

# Known Trade-Offs

## Active game resets after backend restart

The secret target and current attempt count exist only in API memory.

```text
Backend restart:
Active game -> lost
BestScore -> preserved
```

For a multi-instance system, Redis or persistent game-session storage would be appropriate.

## JWT logout

Logout removes the JWT from the browser, but does not revoke an already-issued JWT server-side.

For stronger immediate revocation, refresh tokens and token revocation could be added.

# Interview Explanation

> The React frontend handles presentation and browser state. It communicates with an ASP.NET Core Web API through JSON HTTP requests. Authentication uses JWT Bearer tokens. PostgreSQL stores user credentials as password hashes and stores one nullable `BestScore` field per user. Active games stay server-side in memory so the frontend never knows the secret number. When a game is completed, the backend conditionally updates `BestScore` only when the new attempt count is lower than the existing value.
